Working-directory rules: what it is, and is it for worktrees?

A look at the "Working-directory rules" modal in the app, prompted by the question of whether it's a worktree-specific mechanism or something general enough to group an umbrella project (like Transit Earth) together with its individual prototype sub-projects — and whether it's ready to lean on if you start using git worktree for concurrent sessions.

Short answer

It's a general-purpose, path-pattern tagging layer, not a worktree feature. It tags every indexed session by the literal working directory the agent CLI was launched from, using glob or regex rules you define. It will happily group Transit Earth with its prototypes today, and it will work fine with worktrees once you start using them — but it has no built-in concept of "these five directories are the same git repo." You get that by writing a rule, not by the tool inferring it.

How it actually works

The mechanism is small and entirely path-string based — nothing about it inspects .git, branches, or worktree metadata.

1 · Capture Indexer reads each transcript's cwd — the directory the agent was launched from — straight from the session file the agent already wrote.
2 · Store Every indexed session gets a row with its cwd alongside the session id and agent.
3 · Match Every defined rule (glob or regex) is tested against every session's cwd, case-insensitively.
4 · Tag A session can match more than one rule — tags accumulate, they don't replace each other.
5 · Filter The dashboard's path-tag dropdown filters sessions/charts by any one accumulated tag.

**/quota-service*          → quota-service

Is it tied to git worktrees?

No — and the project's own README says so explicitly. Under "Not here yet," it lists "git-aware worktree canonicalization" as deliberately out of scope for now (README.md:275–280). Nothing in the matching code reads git state; a worktree checked out to its own folder is, as far as this feature is concerned, just another directory that needs its own rule if you want it grouped with the main checkout.

What it gives you for free

  • Any directory, or family of directories, can be tagged with one glob/regex rule.
  • Tags accumulate — a session can belong to a broad group and a narrow one at the same time (e.g. the umbrella project and one specific sub-project).
  • Filtering by tag works the same regardless of why the directories are related — same repo, same client, same worktree convention, whatever.

What it doesn't do automatically

  • No detection that two working directories share a .git history.
  • No auto-tagging when you create a new worktree — you add the rule yourself.
  • No per-branch distinction inside a tag — a rule tags by path, not by what's checked out there.

Grouping an umbrella project with its prototypes

This is exactly what the glob matching is built for. Transit Earth exists on disk as a real sibling project, with prototype sub-projects nested underneath it (prototypes/01-shell/, prototypes/02-ring/, etc., each with its own AGENTS.md/README.md). Because ** in a glob matches arbitrarily deep subdirectories, one rule tags the umbrella project and every prototype together, and an additional narrower rule can also tag one prototype individually — both tags land on the same session at once: 

**/Transit Earth/**                          → transit-earth
**/Transit Earth/prototypes/01-shell*        → te-shell

A session run from inside prototypes/01-shell would carry both transit-earth and te-shell — filter by the broad tag to see everything under the umbrella, or the narrow one to isolate that prototype.

Using it once you adopt worktrees

Nothing about worktrees breaks this — a worktree is just a directory with its own cwd, so sessions run there get indexed exactly like any other. The only thing to plan for is your own naming convention, so one rule can catch every worktree without needing a new rule per branch. For example, if worktrees for this project are always created as siblings named with a shared prefix: 

~/htdocs/ai-usage-observatory/                 (main checkout)
~/htdocs/ai-usage-observatory-wt-feature-x/     (worktree)
~/htdocs/ai-usage-observatory-wt-bugfix-y/      (worktree)

a single rule groups all of them with the main checkout under one tag:

**/ai-usage-observatory*   → ai-usage-observatory

This is in fact already the seeded default rule for this project (see the table above) — it already happens to cover a worktree naming convention like the one above, without any change. If concurrent-task worktrees should be visible separately in the dashboard rather than folded into one tag, add one narrower rule per active worktree (or per naming pattern, e.g. **/ai-usage-observatory-wt-* → wt) alongside the broad one — tags accumulate, so you don't lose the broad grouping by adding the narrow one.

Bottom line

Working-directory rules is a flexible, general path-tagging layer keyed purely on session cwd strings — it groups by directory, for any reason you give it a pattern for. It isn't worktree-aware today (confirmed by the README's own "not here yet" list), but it doesn't need to be: worktrees are still just directories, and one glob per naming convention covers them. It's the same mechanism you'd use to fold Transit Earth's prototypes into one view. If you start experimenting with worktrees, the practical move is to pick a consistent naming convention for the worktree directories up front — that's what makes one rule cover all of them instead of needing to hand-add a rule every time you create one.
